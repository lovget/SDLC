## 1. Введение

Настоящий документ содержит спецификацию требований к настольному приложению NutriTrack. В нём определены назначение продукта, его функции, ограничения, требования к интерфейсам и качеству, а также способы проверки выполнения требований.

### 1.1 Назначение документа

Данная спецификация определяет, **что** должно делать приложение NutriTrack и какими свойствами оно должно обладать. Документ предназначен для разработчика, преподавателя и других участников учебного проекта. Он используется как основа для проектирования, реализации и проверки приложения на протяжении его жизненного цикла.

### 1.2 Область применения продукта

NutriTrack версии 0.2 — настольное приложение для ежедневного учёта питания и планирования рациона. Продукт предназначен для внесения информации о продуктах и приёмах пищи, расчёта калорийности и содержания белков, жиров и углеводов (КБЖУ), планирования питания на семь дней и просмотра динамики показателей.

В область проекта входят ведение дневника питания, расчёт суммарных показателей за день, создание и просмотр недельного плана, а также визуальное представление прогресса. Приложение разрабатывается на языке Java с использованием Swing для графического интерфейса.

В текущую версию не входят облачная синхронизация, интеграция с носимыми устройствами и автоматические медицинские рекомендации. Приложение предназначено для информационного учёта питания и не заменяет консультацию специалиста.

## 2. Обзор продукта

### 2.1 Перспектива продукта

NutriTrack является самостоятельным учебным настольным приложением, разрабатываемым на языке Java с использованием библиотеки Swing. Приложение предназначено для работы на персональном компьютере и предоставляет графический интерфейс для учёта питания и планирования рациона.

В рамках рассматриваемой версии продукт не является частью внешней информационной системы и не требует подключения к сторонним сервисам для выполнения основных функций. Пользовательские данные предполагается хранить локально. Конкретный механизм хранения определяется на этапе проектирования и реализации.

### 2.2 Функции продукта

Основные функции приложения:

1. Добавление, просмотр, редактирование и удаление записей о продуктах и приёмах пищи.
2. Указание количества продукта и его пищевой ценности.
3. Расчёт калорий, белков, жиров и углеводов для отдельных записей.
4. Подсчёт суммарных значений КБЖУ за выбранный день.
5. Просмотр дневника питания за выбранную дату.
6. Создание и редактирование плана питания на семь дней.
7. Просмотр запланированных блюд и приёмов пищи по дням недели.
8. Отображение динамики показателей питания в наглядном виде.
9. Сохранение пользовательских данных между запусками приложения.

### 2.3 Ограничения продукта

- Приложение разрабатывается на языке Java.
- Для графического интерфейса используется библиотека Swing.
- Продукт ориентирован на настольное использование на персональном компьютере.
- Основные функции должны быть доступны без подключения к интернету.
- Данные о продуктах и рационе вводятся пользователем.
- Расчёты выполняются на основании введённых исходных данных; приложение не подтверждает их медицинскую достоверность.
- Облачная синхронизация, интеграция с внешними фитнес-сервисами и функции искусственного интеллекта не входят в текущую версию.

### 2.4 Характеристики пользователей

Основной пользователь — человек, который самостоятельно ведёт учёт питания и планирует рацион. Предполагается наличие базовых навыков работы с персональным компьютером и настольными приложениями. Специальная техническая подготовка не требуется. Пользователь должен иметь возможность добавлять и редактировать данные, выбирать дату, просматривать дневные итоги и недельный план. Разграничение прав доступа в учебной версии не предусматривается.

### 2.5 Допущения и зависимости

- Предполагается запуск приложения на персональном компьютере с совместимой средой выполнения Java.
- Пользователь самостоятельно вводит названия продуктов, их количество и значения пищевой ценности.
- Корректность расчётов зависит от полноты и правильности исходных данных.
- Для графического отображения и локального хранения могут использоваться дополнительные библиотеки или программные средства; конкретный выбор фиксируется при реализации.
- Отсутствие подключения к интернету не должно препятствовать основным функциям приложения.

## 3. Требования

Требования сформулированы как проверяемые утверждения. Для каждого требования указан уникальный идентификатор, обоснование, критерий приёмки и метод проверки. Требования описывают ожидаемое поведение приложения, не фиксируя внутреннюю реализацию, если она не является обязательным ограничением.

### 3.1 Внешние интерфейсы

#### 3.1.1 Пользовательские интерфейсы

Приложение должно предоставлять графический интерфейс настольного типа, реализованный с использованием Java Swing. Основные разделы интерфейса должны обеспечивать доступ к дневнику питания, расчёту КБЖУ, недельному планированию и просмотру прогресса.

Интерфейс должен содержать элементы для ввода названия продукта, количества, даты и сведений о приёме пищи. Для отображения результатов могут использоваться таблицы, списки, текстовые поля и графические элементы. При некорректном вводе приложение должно показывать понятное сообщение об ошибке и предоставлять возможность исправить данные.

#### 3.1.2 Аппаратные интерфейсы

Специальные аппаратные интерфейсы не предусмотрены. Приложение использует стандартные средства персонального компьютера: экран, клавиатуру и устройство управления указателем. Подключение специализированных датчиков, весов или носимых устройств в текущую версию не входит.

#### 3.1.3 Программные интерфейсы

Приложение должно выполняться в совместимой среде Java и использовать библиотеку Swing для построения пользовательского интерфейса. Внешние сетевые API и интеграции со сторонними сервисами в текущей версии не предусмотрены. Средство локального хранения данных определяется на этапе реализации.

### 3.2 Функциональные требования

#### REQ-FUNC-001 — Добавление записи о питании

- **Title:** Добавление записи о питании.
- **Statement:** Система должна предоставлять пользователю возможность добавить запись о продукте или приёме пищи с указанием названия, количества и пищевой ценности.
- **Rationale:** Добавление записей является основой ведения дневника питания.
- **Acceptance Criteria:** После заполнения обязательных полей и подтверждения ввода новая запись отображается в дневнике выбранной даты. При отсутствии обязательных данных запись не сохраняется, а пользователь получает сообщение об ошибке.
- **Verification Method:** Test.
- **More Information:** Связано с REQ-FUNC-002 и REQ-FUNC-003.

#### REQ-FUNC-002 — Просмотр и изменение дневника питания

- **Title:** Просмотр и изменение дневника питания.
- **Statement:** Система должна позволять пользователю просматривать записи дневника питания за выбранную дату, изменять сведения о записи и удалять её.
- **Rationale:** Пользователь должен иметь возможность контролировать и корректировать внесённую информацию.
- **Acceptance Criteria:** При выборе даты отображаются относящиеся к ней записи. После изменения данные обновляются. После подтверждения удаления выбранная запись исчезает из списка.
- **Verification Method:** Test.
- **More Information:** Относится к модулю дневника питания.

#### REQ-FUNC-003 — Расчёт калорий и КБЖУ

- **Title:** Расчёт калорий и КБЖУ.
- **Statement:** Система должна рассчитывать калорийность, количество белков, жиров и углеводов для добавленных продуктов с учётом указанного количества, а также отображать суммарные значения за выбранный день.
- **Rationale:** Расчёт позволяет пользователю оценивать пищевую ценность рациона.
- **Acceptance Criteria:** Для тестового набора продуктов с известными исходными значениями система отображает рассчитанные значения и корректную сумму за день. При изменении количества продукта итоговые значения пересчитываются.
- **Verification Method:** Test.
- **More Information:** Расчёт выполняется на основании введённых пользователем данных.

#### REQ-FUNC-004 — Планирование питания на неделю

- **Title:** Планирование питания на неделю.
- **Statement:** Система должна предоставлять пользователю возможность создавать, просматривать и изменять план питания на семь последовательных дней.
- **Rationale:** Недельное планирование помогает заранее распределять приёмы пищи.
- **Acceptance Criteria:** Пользователь может выбрать день недели, добавить к нему запланированные продукты или блюда, просмотреть план на все семь дней и изменить ранее созданную запись.
- **Verification Method:** Test.
- **More Information:** План питания отделён от фактических записей дневника питания.

#### REQ-FUNC-005 — Визуализация прогресса

- **Title:** Визуализация прогресса.
- **Statement:** Система должна отображать динамику показателей питания за выбранный период в графическом или ином наглядном виде.
- **Rationale:** Визуализация помогает анализировать изменения показателей питания.
- **Acceptance Criteria:** При наличии сохранённых данных пользователь может выбрать доступный период и увидеть графическое представление калорийности и КБЖУ. При отсутствии данных система отображает понятное сообщение.
- **Verification Method:** Demonstration, Test.
- **More Information:** Показатели должны соответствовать данным дневника питания.

#### REQ-FUNC-006 — Сохранение пользовательских данных

- **Title:** Сохранение пользовательских данных.
- **Statement:** Система должна сохранять записи дневника питания и недельного плана между завершением и повторным запуском приложения.
- **Rationale:** Пользователь не должен повторно вводить ранее сохранённые сведения.
- **Acceptance Criteria:** После добавления и сохранения тестовых записей, закрытия и повторного запуска приложения ранее внесённые данные доступны для просмотра.
- **Verification Method:** Test.
- **More Information:** Используется локальное хранение; конкретный механизм определяется при реализации.

#### REQ-FUNC-007 — Проверка корректности вводимых данных

- **Title:** Проверка корректности вводимых данных.
- **Statement:** Система должна проверять обязательные поля и допустимость числовых значений перед сохранением записи.
- **Rationale:** Проверка предотвращает сохранение неполных или некорректных данных.
- **Acceptance Criteria:** При вводе пустого названия, отрицательного количества или значения неподходящего формата система не сохраняет запись и отображает сообщение с указанием причины.
- **Verification Method:** Test.
- **More Information:** Проверка применяется к формам добавления и редактирования данных.

### 3.3 Качество обслуживания

#### 3.3.1 Производительность

- **REQ-PERF-001:** Система должна открывать основные разделы интерфейса не более чем за 2 секунды при обычном объёме тестовых данных на целевом персональном компьютере.
- **REQ-PERF-002:** Пересчёт дневных итогов КБЖУ после добавления или изменения записи должен выполняться не более чем за 1 секунду при наличии до 100 записей за выбранный день.

**Verification Method:** Test, Analysis. Время измеряется на одном и том же тестовом окружении.

#### 3.3.2 Безопасность

- **REQ-SEC-001:** Система должна проверять пользовательский ввод и предотвращать сохранение заведомо некорректных значений.
- **REQ-SEC-002:** Система не должна передавать пользовательские записи о питании во внешние сетевые сервисы в рамках текущей версии.
- **REQ-SEC-003:** Система должна сохранять локальные данные при штатном завершении работы приложения.

**Verification Method:** Test, Inspection. Учётные записи и удалённая аутентификация в текущей версии не предусматриваются.

#### 3.3.3 Надёжность

- **REQ-REL-001:** Система должна сохранять ранее подтверждённые пользовательские записи при штатном закрытии и повторном запуске приложения.
- **REQ-REL-002:** При обнаружении некорректных данных система должна сообщать об ошибке и не должна завершаться аварийно только из-за ошибочного пользовательского ввода.

**Verification Method:** Test.

#### 3.3.4 Доступность

NutriTrack является настольным приложением. Доступность функций зависит от возможности запуска приложения на персональном компьютере и наличия совместимой среды Java. Круглосуточная доступность, серверные соглашения SLA и удалённый доступ не предусматриваются.

- **REQ-AVAIL-001:** При успешном запуске приложения основные функции дневника питания, расчёта КБЖУ и недельного планирования должны быть доступны без подключения к интернету.

**Verification Method:** Demonstration, Test.

#### 3.3.5 Наблюдаемость

- **REQ-OBS-001:** При возникновении ошибки ввода или операции сохранения система должна отображать пользователю сообщение, позволяющее определить характер проблемы.
- **REQ-OBS-002:** Сообщения об ошибках не должны содержать технические сведения, не предназначенные для обычного пользователя, например полный стек вызовов.

**Verification Method:** Test, Inspection.

### 3.4 Соответствие стандартам

Специальные отраслевые сертификаты и внешние протоколы соответствия для учебной версии NutriTrack не требуются. Документация проекта оформляется в соответствии со структурой предоставленного шаблона SRS и требованиями методических указаний к лабораторной работе. Идентификаторы требований должны быть уникальными, а формулировки — однозначными и проверяемыми.

### 3.5 Проектирование и реализация

#### 3.5.1 Установка

Приложение должно запускаться на персональном компьютере при наличии совместимой среды выполнения Java. Порядок подготовки среды и запуска приложения должен быть описан в проектной документации. Конкретный способ упаковки и установки определяется на этапе реализации.

#### 3.5.2 Сборка и поставка

Исходный код проекта должен храниться в Git-репозитории. Изменения фиксируются отдельными коммитами с осмысленными сообщениями. Для сборки приложения используется выбранная конфигурация Java. Инструкции по сборке и запуску включаются в документацию после определения используемых инструментов.

#### 3.5.3 Распределение

Приложение предназначено для локального запуска на одном персональном компьютере. Распределённое развёртывание, серверная инфраструктура, репликация и синхронизация между устройствами в текущую версию не входят.

#### 3.5.4 Сопровождаемость

- **REQ-MAINT-001:** Исходный код должен быть разделён на логически самостоятельные классы и компоненты, отвечающие за модель данных, обработку действий пользователя и отображение интерфейса.
- **REQ-MAINT-002:** Имена классов, методов и переменных должны отражать их назначение, а структура проекта должна обеспечивать возможность дальнейшего изменения и расширения функций.
- **REQ-MAINT-003:** Основные функции и порядок запуска приложения должны быть описаны в README-файле репозитория.

**Verification Method:** Inspection.

#### 3.5.5 Повторное использование

При реализации допускается повторное использование общих компонентов приложения, например элементов ввода, представления записей питания и средств расчёта КБЖУ. Выделение таких компонентов должно уменьшать дублирование кода и упрощать сопровождение. Создание отдельной универсальной библиотеки в рамках текущей версии не требуется.

#### 3.5.6 Переносимость

Приложение должно использовать стандартные средства Java и Swing, чтобы обеспечить возможность запуска на операционных системах, поддерживающих выбранную версию Java. Фактический перечень проверяемых операционных систем определяется доступным тестовым окружением.

#### 3.5.7 Стоимость

Проект является учебной разработкой. Отдельный бюджет на приобретение серверных ресурсов или платных внешних сервисов не предусматривается. Предпочтительно использовать доступные инструменты разработки и библиотеки с подходящими условиями лицензирования.

#### 3.5.8 Сроки

Работа выполняется в рамках сроков лабораторной работы № 3 по дисциплине «Жизненный цикл разработки программного обеспечения». Основные этапы включают сбор требований, подготовку диаграмм SysMLv2, заполнение SRS, проверку документации и согласование изменений посредством Pull Request.

#### 3.5.9 Доказательство концепции

В рамках учебного проекта проверка концепции заключается в демонстрации основных сценариев: добавления записи о питании, расчёта дневных значений КБЖУ, составления недельного плана и отображения прогресса. Результаты демонстрации фиксируются после фактической реализации и проверки соответствующих функций.

#### 3.5.10 Управление изменениями

Изменения требований и документации должны вноситься в отдельной Git-ветке. Каждое логически завершённое изменение фиксируется коммитом. Для проверки и согласования изменений используется Pull Request. Замечания участников рассматриваются, а необходимые исправления вносятся до согласования слияния. Согласованные изменения отражаются в таблице истории изменений.

### 3.6 ИИ/МО

В текущей версии NutriTrack технологии искусственного интеллекта и машинного обучения не используются. Расчёт калорий и КБЖУ выполняется по заданным формулам на основании данных, введённых пользователем. Автоматическое распознавание продуктов, генерация рациона с помощью моделей и прогнозирование на основе машинного обучения не входят в область проекта.

Подразделы 3.6.1–3.6.6 не применяются к текущей версии продукта.
